# Настройка

Setup и init эквивалентны. Начни с планирования и чтения проекта.

1. Найди инструкции, манифесты, документы и CI. Отсутствие .git допустимо.
2. Всегда спроси **local или github**. При повторе попроси подтвердить
   текущий режим или изменить его; не угадывай по origin.
3. Спроси цель проекта, пользователя результата и критерии успеха.
   Существующую цель прочитай и согласуй.
4. Из цели предложи задачи, критерии готовности и зависимости. Состав
   согласует пользователь. Не добавляй демо-задачи и не считай обсуждение одобрением.
5. В local явно согласуй использование Git. Без Git не требуй git/gh/ветки.
   С Git согласуй ветки и локальную интеграцию. Для github проверь git, gh,
   identity, origin и owner/repo. Remote не меняй без запроса.
6. Покажи полный [профиль](configuration.md), документы, исполнителя,
   команды test/unit/integration/e2e/lint/build и ревьюеров.
   Jira подключается по запросу и разрешению на MCP.
   Создание репозитория требует явного owner/имени/видимости.
7. Предложи точный [Project Instructions](../assets/PROJECT_INSTRUCTIONS.md)
   для AGENTS.md и [правила Git](git.md) выбранного режима.
   Сохрани остальные инструкции, согласуй конфликты, исключи дубли.
   CLAUDE.md и GEMINI.md ссылаются на AGENTS.md.
8. После одобрения создай только согласованные файлы в рабочей ветке
   либо local без Git. Сравни текущий файл с прочитанным перед записью.
   При Git добавь в .gitignore .etask/state.json и .etask/runs/.
9. Создай бэклог и Markdown-доску с четырьмя согласованными статусами.
10. После каждой правки выполни review и санитайз, затем проверки профиля,
    путей и инструментов. Покажи готовность и команду следующей задачи.

Не устанавливай инструменты за рамками согласованного изменения.
Отсутствие инструмента — явный блокер, не повод для незаявленного fallback.
Bootstrap пустого Git-репозитория согласуется отдельно.

## Релизы

При GitHub добавь в AGENTS.md Conventional Commits и обязательный
semantic-release после каждого согласованного merge integration → production.
Релиз содержит новую версию и список изменений. Предложи конкретный workflow
для стека проекта; не копируй механизм упаковки every-task в любой продукт.
Мерж production по-прежнему требует явной команды пользователя.
