# Настройка

Прочитай [конфигурацию](configuration.md) и [Git-процесс](git.md).
Режим setup безопасен при повторном запуске.

1. Найди корень целевого Git-проекта, инструкции агентов, манифесты,
   CI, бэклог и документацию. Проверь git, gh, Git identity, origin,
   авторизацию `gh api user` и наличие dev. В plan mode ограничься чтением.
2. Если `.etask/config.json` есть, прочитай и проверь её по схеме.
   Сохрани все корректные значения. При несовместимой версии опиши
   необходимую миграцию и дождись решения.
3. Определи команды тестов, линтера и сборки по существующим CI/манифестам.
   Для каждой укажи рабочий каталог. Неизвестную команду уточни у пользователя.
   Для неприменимой проверки предложи конкретное обоснование пропуска.
4. Покажи предлагаемый JSON, создаваемые/меняемые файлы и связь с найденным
   окружением. Jira по умолчанию выключена. Если пользователь хочет включить
   её, прочитай [Jira](jira.md), уточни профиль и явное разрешение на MCP.
5. Дождись подтверждения конкретной конфигурации и файлов. В существующем
   репозитории любые изменения делай в отдельной рабочей ветке от dev
   либо в уже согласованной ветке текущей задачи. Не меняй main/dev.
6. Создай `.etask/config.json` и только согласованные отсутствующие документы
   на основе структуры шаблонов в assets. Заполняй бэклог реальными задачами
   пользователя, а при их отсутствии создай пустой каркас. Пример ET-1
   остаётся примером до явного выбора пользователя. Повторно сравни существующий файл перед
   записью, чтобы сохранить параллельные изменения пользователя.
7. Добавь согласованную ссылку на etask в существующие инструкции проекта.
   Сохрани остальное содержимое. При наличии AGENTS.md файлы CLAUDE.md
   и GEMINI.md должны ссылаться на него. Установка навыка доступна по
   механизму хоста и не требует абсолютных путей исходной машины.
8. Проверь JSON, пути и наличие команд. Запуск проверок выполняй в рамках
   одобренной настройки. Инструменты и зависимости устанавливай после
   отдельного разрешения, если их установка меняет окружение пользователя.
9. Покажи таблицу готовности и команду вызова etask для текущего агента.
   Коммит, push и PR конфигурации подчиняются общему процессу.

Если dev отсутствует, покажи фактические ветки и запроси решение о базовой
ветке до изменений. Для нового пустого репозитория предложи однократную
инициализацию в рабочей ветке, создание main/dev на первом коммите через
`gh api` и продолжение работы в рабочей ветке. Создание публичного репозитория
требует явного выбора владельца и видимости пользователем.

Авторизацию выполняет пользователь средствами gh или настроенного хоста.
Не запрашивай токены в чате. При ошибке сети или sandbox используй штатный
запрос разрешения окружения, если он доступен, затем повтори ту же операцию.
