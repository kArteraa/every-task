# Выполнение задачи

Прочитай [конфигурацию](configuration.md) и [Git-процесс](git.md).
Держи список этапов с текущим статусом, проверенными SHA и результатами.
Действуй последовательно. При ошибке обязательного этапа объясни блокер.

## 0. Задача и ветка

Прочитай `.etask/config.json`. При ошибке или отсутствии предложи setup.
Пустой вызов выбирает первую задачу текущего пользователя или `any` в
очереди, у которой выполнены зависимости и нет открытого/смёрженного PR.
Если у задачи есть открытый PR, пустой вызов пропускает её как in-review,
а явный вызов с ID продолжает её. Покажи выбранный ID и причину выбора.

Для явного ID прочитай полный блок задачи и связанные документы.
Свободное описание преобразуй в новую задачу по правилам конфигурации.
Проверь каждую зависимость через смёрженный PR в dev. Для явного вызова
с незавершёнными зависимостями покажи блокеры и дождись решения.

До переключения ветки и записи Jira определи фазу продолжения по запросу,
PR, комментариям, локальному HEAD и удалённому head.

- PR уже MERGED в dev — сообщи о завершении, проверь только остаток очистки
  и синхронизации через режим review. Новая работа требует новой задачи.
- PR закрыт без мержа — покажи состояние и уточни дальнейшее действие.
- PR открыт, изменения уже отправлены, новых требований/замечаний на
  исправление нет — продолжи только недостающие действия доставки из этапа 6.
  Сохрани достигнутый статус inReview. Если статус ещё inProgress,
  доведи доставку до inReview после проверки PR. Новый план, коммиты и push
  в этом случае не нужны.
- Пользователь запросил изменения или продолжение исправлений по конкретным
  замечаниям — продолжи реализацию с планом исправлений и статусом inProgress.
  Расхождение локального HEAD и PR head сначала объясни пользователю.

Проверь дерево, origin и пользователя. Для существующего PR прочитай
замечания и проверь соответствие branch/base/ID. Переключись через
`gh pr checkout <номер> --repo owner/repo`. Для новой задачи создай ветку
от актуального dev. В plan mode сначала подготовь план чтением и перенеси
переключение ветки/запись задачи на момент выхода из режима.

При начале или фактическом продолжении реализации, если Jira включена
и её использование разрешено, проверь задачу, назначь текущего
Jira-пользователя и переведи в статус работы.
Используй [процедуру Jira](jira.md). При возобновлении сверяй состояние
и выполняй только недостающие действия.

## 1. План и первое подтверждение

Покажи ID, цель, критерии готовности, файлы/области изменений, проверки,
контракты, риски и новые решения. Сверься с журналом решений проекта.
Дождись одобрения до реализации. Уточнения, меняющие существенную область
работ, отражай в обновлённом плане и согласуй.

## 2. Реализация и коммиты

| Тип | Проверка реализации |
| --- | --- |
| feat | Падающий тест нового поведения, затем реализация |
| fix | Падающий регрессионный тест, затем исправление |
| refactor | Существующие проверки зелёные до и после |
| contract | Контрактный тест, схемы, реализации, потребители и документация |
| test | Показать, что новый тест обнаруживает предполагаемую ошибку |
| docs/chore | Проверки затронутой документации/конфигурации |

Если проект имеет специальные правила тестирования UI и контрактов,
применяй их. Чистая вёрстка требует подходящей проверки рендера и сборки.
Сначала докажи нужное поведение, затем выполни небольшие фокусные коммиты.

## 3. Чистка

- Изменения соответствуют одобренному плану.
- Общая логика использует принятые в проекте границы модулей.
- Имена, функции и конфигурация понятны следующему разработчику.
- Временные заглушки и отладочные фрагменты убраны.
- Новые зависимости обоснованы, lock-файлы и лицензии обновлены.
- Новые решения зафиксированы в согласованном журнале.

Закоммить результат чистки, если есть изменения.

## 4. Проверки

Выполни test, lint и build из конфигурации в соответствующих cwd.
Для явно пропущенной проверки покажи согласованную причину.
Проверь изменение генерируемых файлов и включи актуальные артефакты,
если их хранение требуется проектом. Выполни дополнительные проверки,
указанные в критериях задачи или CI.

Падение в затронутом коде исправь и повтори проверку. Падение в постороннем
коде сообщи пользователю и останови доставку. Ошибку среды не превращай
в успешную проверку. После исправлений снова проверь итоговое состояние.

## 5. Ревью

Проверь diff относительно dev, критерии готовности, границы импортов,
контракты, обработку ошибок, секреты, зависимости и актуальность документации.
Убедись, что тесты проверяют поведение и могут обнаружить регрессию.
Исправь замечания, повтори относящиеся к ним проверки и полный набор перед push.

Запиши ручные сценарии в `paths.manualChecks` по
[шаблону](../assets/MANUAL_CHECKS.example.md). У каждого есть ID задачи,
шаги, ожидаемый результат, признаки провала и фактический статус проверки.
Непроверенный вручную сценарий обозначь как pending. Покажи его в ответе и PR.
Ожидание ручного прогона перед push нужно только если этого требуют критерии проекта.

Закоммить итог. Зафиксируй команды, результаты и финальный HEAD.
Проверь чистоту дерева и принадлежность текущей ветки.

## 6. Push и второе подтверждение

Покажи краткий итог, результаты проверок, ручные сценарии, ветку и HEAD.
Запроси разрешение на push этого коммита и создание/обновление PR в dev.
Дождись ответа. Одобрение плана не является разрешением на push.

Перед отправкой повторно проверь HEAD и дерево. Если они изменились,
повтори проверки и подтверждение. После разрешения отправь рабочую ветку.
Найди существующий PR по head/base/ID, затем создай недостающий или обнови
имеющийся. Добавь ревьюеров из конфигурации, исключив автора.

При включённой Jira переведи задачу в статус проверки и добавь ссылку на PR.
При частичном сбое сообщи успешные действия и остаток работы. На следующем
запуске сверь реальное состояние до повторения внешних операций.

Заверши ссылкой на PR, ID и командой `etask review <ID>` для текущего агента.
Мерж — отдельный [режим ревью](review.md) с третьим подтверждением.
