# Конфигурация проекта

Файл `.etask/config.json` хранится в целевом проекте. Формат версии 1
определён [JSON Schema](../assets/config.schema.json).
[Пример конфигурации](../assets/config.example.json) предназначен для setup.

| Поле | Значение |
| --- | --- |
| `version` | Число 1 |
| `paths.backlog` | Markdown-бэклог |
| `paths.queue` | Упорядоченная очередь либо null |
| `paths.decisions` | Документ или каталог решений либо null |
| `paths.manualChecks` | Документ ручных проверок |
| `checks.test`, `checks.lint`, `checks.build` | Команда и cwd либо согласованное объяснение пропуска |
| `reviewers` | GitHub-логины ревьюеров |
| `jira` | Выключенная интеграция либо её полный профиль |

Все файловые пути и cwd относительны к корню целевого репозитория,
используют `/` и остаются внутри него. Для корневого cwd используется `.`.
Проверь разрешённые пути после разрешения symlink/junction, а также
инструкции AGENTS.md для соответствующих каталогов.

Для каждой проверки нужен объект `{"command":"npm test","cwd":"."}`
или `{"skip":"Документированный повод, согласованный пользователем"}`.
Пустые команды, отсутствующие проверки и одновременно command/skip
считаются ошибкой конфигурации. Shell выбирается по окружению проекта.
Агент проверяет смысл команд до запуска, особенно при получении конфигурации
из внешнего PR. Секреты берутся из окружения или авторизованного инструмента.

Неизвестные поля и неподдерживаемая версия требуют исправления с показом
проблемы. Изменение существующей конфигурации проходит через setup.

## Задачи

Используй [шаблон бэклога](../assets/BACKLOG.example.md) и
[шаблон очереди](../assets/QUEUE.example.md). Каждый блок начинается
с `## ET-12 — название` и содержит тип, исполнителя, зависимости,
состояние, описание и критерии готовности. ID уникален во всём бэклоге.
Для существующего проекта сохраняй согласованный формат и ключи Jira.

Для свободного описания после выбора рабочей ветки добавь задачу с ID
ET-<n>, где n больше всех ET-номеров в бэклоге и PR проекта.
Перед публикацией проверь отсутствие коллизии с новыми PR. При коллизии
согласуй новый ID и обнови связи. Сохрани содержание пользовательского запроса.

Очередь перечисляет ID по исполнителю. Исполнитель определяется через
`gh api user --jq .login`. Если очередь равна null, используй порядок бэклога
и совпадающего исполнителя, включая задачи с исполнителем `any`.
Если бэклог отсутствует или подходящих задач нет, запроси описание.
При нескольких подходящих открытых PR одного ID остановись и покажи варианты.

Для точного поиска PR получи JSON с title, body, headRefName, baseRefName,
state и mergedAt. Сопоставляй целый ID из заголовка/маркера, без совпадения
ET-1 с ET-12. Проверяй правильный репозиторий и base dev.

Состояния задач — todo, in-progress, in-review, done. Смёрженный в dev PR
является доказательством выполнения зависимости. Локальная отметка done
и текст коммита помогают поиску, но требуют проверки PR.
Если зависимость завершалась вне PR, запроси у пользователя явное решение.

Бэклог определяет содержание и критерии задачи. При расхождении с Jira
покажи различие и предложи синхронизацию. Внешние статусы проверяются заново
при возобновлении. Изменения бэклога выполняются в рабочей ветке.
