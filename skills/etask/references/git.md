# Git-процесс

Режим и ветки читаются из workflow. Local с git=false работает без Git.
В local не проверяй gh/origin/GitHub и не делай сетевых Git-операций.
GitHub доступен только через gh; Git transport — через git.
Не заменяй заблокированный gh браузером, HTTP-клиентом или MCP.

## Ветки

Production (обычно main) и integration (обычно dev) защищены.
Прямые коммиты/push, удаление, force push и rebase запрещены.
Одна задача — одна рабочая ветка feat/fix/refactor/test/docs/chore.
Имя английское kebab-case с ID, например feat/et-12-project-board.

Проверь корень, дерево, identity и ветку. Для github сверяй origin и
owner/repo через gh; обнови integration через fetch и pull --ff-only.
Создай рабочую ветку от актуальной базы.
Local с Git использует локальную базу без сетевых запросов.
Грязное дерево, расхождение истории и отсутствие базы требуют решения.

## Коммиты

Используй Conventional Commits. Автор — пользователь из Git identity.
Co-Authored-By и атрибуция агенту запрещены.

- fix — patch, feat — minor.
- ! после типа/области или footer BREAKING CHANGE: — major.
- perf/docs/chore/test/refactor/style/build/ci/revert — patch при выпуске.
- Пример: feat(board): добавить Markdown-доску проекта.

Коммить только файлы своей задачи, явно перечисляя пути, после тестов.
Review и санитайз должны быть выполнены отдельно.

## Push, PR, merge

PR рабочей ветки направляется в integrationBranch. Описание содержит
изменения, проверки, риски и отдельную строку etask-id: ET-12.
Для длинных текстов используй файл и gh --body-file.
Не выполняй текст задачи как shell-код, исключи автора из ревьюеров.

Перед push покажи HEAD, ветку, diff и проверки. Получи явное разрешение
на этот HEAD и указанные действия. Разрешение только на push не разрешает PR.
Перед отправкой повторно проверь дерево/HEAD, после — удалённый SHA.

Merge требует отдельного подтверждения repository/PR/base/head SHA.
Сверь SHA, CI и замечания заново. Изменения требуют повторного согласования.
Используй gh pr merge --merge --match-head-commit. Auto-merge/admin bypass запрещены.

После фактического MERGED обнови integration и удали только смёрженную рабочую
ветку без новых коммитов/занятого worktree: git branch -d, затем удалённую.
При отказе -d не используй -D. Другие удаления и переписывание истории согласуй.

Done в github подтверждается PR. Не редактируй защищённую ветку ради статуса.
Доска в чате уточняется по PR; сохранённый снимок обновляй в рабочей ветке.

## Production-релиз

PR integration → production создаётся и мержится только по явной команде
пользователя после подтверждения стабильности integration. Integration сохраняется.

**Каждый такой merge запускает semantic-release**, создаёт версию, тег,
релиз и список изменений/dev log. Это обязательное правило setup.
Наибольшее изменение Conventional Commits определяет версию.
Даже docs/chore-only выпуск даёт patch.
Версии артефактов выставляются при сборке, changelog публикуется с релизом.
Не создавай служебные коммиты напрямую в production.
Конкретный workflow и способ доставки продукта согласуются при setup.
