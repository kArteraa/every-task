# Git-процесс

## Перед изменениями

Определи репозиторий через `git rev-parse --show-toplevel`, текущую ветку
и состояние через `git status --short --branch`. Для GitHub используй
`gh repo view --json nameWithOwner` и далее передавай `--repo owner/repo` явно.
Убедись, что origin относится к этому репозиторию. Если есть изменения,
покажи их и согласуй продолжение. Сохраняй чужую работу.

main — production, dev — интеграция. Прямые коммиты, push, force-push,
rebase и удаление этих двух веток запрещены.

Одна задача выполняется в одной ветке. Для новой задачи после проверки
зависимостей выполни последовательно, останавливаясь при первой ошибке.

```sh
git fetch origin
git switch dev
git pull --ff-only origin dev
git switch -c feat/et-12-filter-events
```

Если локальной dev нет, но origin/dev существует, создай отслеживающую ветку
через `git switch --track origin/dev`. Если dev отсутствует на сервере,
предложи настройку веток. Расхождение локальной и удалённой dev требует
решения пользователя. Если текущая рабочая ветка уже существует, проверь
её связь с задачей и PR, затем продолжи её.

Имя ветки — `<тип>/<id-в-нижнем-регистре>-<slug>`. slug состоит из 2–4
английских слов в kebab-case. Допустимы feat, fix, refactor, test, docs, chore.
Тип contract использует `feat/<id>-contract-<slug>`.

## Коммиты и PR

Коммить только файлы своей задачи, явно перечисляя пути. Сообщения — простой
список на языке проекта, например `- Добавить фильтр событий`.
Автор — пользователь из существующей Git-конфигурации. Если identity
не настроена, запроси её. Атрибуция агенту и Co-Authored-By запрещены.

Заголовок PR — `<ID> · <название>`, base всегда dev. В описании выдели
изменения, проверку критериев готовности, ручные сценарии и риски.
Добавь отдельную строку `etask-id: ET-12` с фактическим ID.
Этот маркер, head и base используются для точной связи задачи с PR.
Список ревьюеров берётся из конфигурации. Исключи автора PR.

Для длинного описания создай временный файл и передай `--body-file`.
Аргументы `gh` и пути передавай отдельными аргументами с корректным
экранированием для текущего shell. Текст задачи не выполняется как shell-код.

Перед push рабочее дерево должно быть чистым, проверки зелёными,
а пользователь должен видеть точный HEAD, ветку и список изменений.
Разрешение действует на этот HEAD. Если HEAD или содержимое изменилось,
повтори соответствующие проверки и согласование push.

Push выполняется только для текущей проверенной рабочей ветки,
например `git push -u origin feat/et-12-filter-events`.
После него сверяй локальный HEAD с удалённым.

## Мерж и очистка

Мерж выполняется после [ревью](review.md) и явного разрешения на конкретные
repository, PR, base и head SHA. Используй merge-коммит и защиту от смены head.

```sh
gh pr merge 42 --repo owner/repo --merge --match-head-commit CHECKED_SHA
```

Не включай auto-merge, обход защиты или административный bypass.
Проверь через `gh pr view`, что PR действительно MERGED в dev с проверенным
head. При изменении base после проверки обнови проверки перед мержем.
Если GitHub блокирует мерж, сообщи причину.

После успешного мержа и при чистом дереве переключись на dev, обнови её
через `git pull --ff-only origin dev`, удали локальную рабочую ветку через
`git branch -d <ветка>`, затем удалённую через `git push origin --delete <ветка>`.
Перед удалением проверь точное имя, принадлежность PR, отсутствие новых
коммитов и соответствие удалённого head смерженному SHA. Если ветка уже
удалена, отметь это и продолжи оставшиеся шаги. Отказ `-d` требует проверки,
а не замены на `-D`. Не удаляй ветку, занятую другим worktree.

Удаление других веток и переписывание истории требуют отдельного разрешения.
PR dev → main создаётся исключительно по отдельной команде пользователя
после подтверждения стабильности dev. После выпуска dev сохраняется.
