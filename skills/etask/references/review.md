# Ревью и мерж

Прочитай [Git-процесс](git.md), [конфигурацию](configuration.md), задачу
и относящиеся к ней решения. При включённой Jira прочитай [Jira](jira.md).

1. Найди PR с точным ID, правильным репозиторием и base dev. Несколько
   совпадений требуют уточнения. Если PR уже MERGED, проверь head/base
   и выполни только оставшуюся разрешённую очистку и синхронизацию.
   Закрытый без мержа PR требует решения пользователя.
2. При чистом рабочем дереве получи ветку PR. Сохрани исходную ветку,
   чтобы вернуться к ней после ревью с замечаниями. Обнови сведения
   о dev. Зафиксируй repository, PR, head SHA и текущий base SHA.
3. Прочитай diff, комментарии и критерии задачи. Выполни чек-лист ревью
   из [пайплайна](pipeline.md) и все настройки checks. Перед запуском
   команд из чужого PR проверь их содержание и правила доверия проекта.
4. Проверь `gh pr checks`. Если проверки ещё идут, дождись завершения
   с обновлениями пользователю. Если CI для проекта не настроен,
   явно укажи это и результаты локальных проверок. Падающий обязательный
   CI блокирует мерж. Защита ветки остаётся обязательной.
5. Покажи найденные замечания и ручные сценарии задачи со статусами.
   При замечаниях сравни автора PR с текущим пользователем GitHub.
   Если автор другой, подготовь конкретный текст review и отправь
   request-changes в рамках явно вызванного режима review.
   Для собственного PR покажи замечания в ответе и команду продолжения
   по ID, пропустив отправку request-changes, которую GitHub запрещает автору.
   Верни Jira в статус работы, если интеграция разрешена, и укажи автору
   команду продолжения по ID. В чужую ветку правки автоматически не добавляй.
6. При готовности покажи проверенные SHA и запроси мерж конкретного PR в dev.
   Дождись явного ответа. Предыдущее разрешение на push не разрешает мерж.
7. После подтверждения повторно проверь head, base, состояние PR, CI и
   чистоту дерева. При изменениях обнови ревью/проверки и запроси новое
   подтверждение. Убедись, что обязательные ручные проверки завершены.
8. Если пользователь не автор PR, отправь approve, затем выполни мерж
   с `--match-head-commit` по [Git-процессу](git.md). При авторстве
   пользователя пропусти approve. Дождись подтверждённого MERGED.
9. Обнови dev, удали только смёрженную рабочую ветку по Git-процессу,
   синхронизируй Jira и сообщи итог со ссылкой на PR.

Состояние done в Markdown можно вывести из смёрженного PR при следующем
чтении бэклога. Если требуется записать done в файл после мержа, это отдельное
изменение в рабочей ветке с PR в dev. Прямое редактирование dev запрещено.
