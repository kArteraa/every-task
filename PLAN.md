# etask — план реализации версии 0.1.0

## Цель и согласованные решения

Создать публичный репозиторий `kArteraa/every-task` с рабочим плагином
`etask` для Codex, Claude Code и Gemini CLI. Лицензия MIT.
Исходная рабочая папка находится в `D:\Web\lib\every-task`.

Основой служит `D:\Web\www\AlphaImpact\docs\PIPELINE.md` и адаптеры
команд этого проекта. Переносимые инструкции включаются в пакет etask,
чтобы установка работала без доступа к AlphaImpact.

Согласованы три остановки с ожиданием ответа пользователя.

1. Одобрение плана.
2. Разрешение на push проверенного коммита.
3. Разрешение на мерж проверенного PR.

Jira подключается по выбору проекта. Без неё доступны задачи из текста
пользователя и Markdown-бэклога. Документация пишется на русском,
код и идентификаторы на английском. Инструменты разработки используют
Node.js 22 и встроенный test runner. Пайплайн выполняется агентом через
его инструменты, Git, GitHub CLI и опциональный Atlassian MCP.

## Передача работы на другое устройство

Этот файл сохраняет одобренный план. Реализация плагина ещё предстоит.
Пользователь разрешил закоммитить и отправить план в `feat/etask-plugin`.
Разрешение относится к публикации плана. Мерж требует отдельного ответа.

При продолжении работы взаимодействовать с GitHub только через GitHub CLI
(`gh`), а Git-операции выполнять через `git`. Если CLI заблокирован,
сообщить причину. Использовать MCP-серверы только после явного разрешения
пользователя в сообщении и в пределах указанной им задачи и сервера.

На исходной машине выполнен `git init -b feat/etask-plugin`. Предыдущие
попытки записи блокировались ошибкой среды
`helper_unknown_error: setup refresh had errors`. После восстановления
запуска команд Git сообщил, что репозиторий создан пользователем
CodexSandboxOffline, а текущий процесс работает от misha. Для этого
известного репозитория допустима точечная настройка safe.directory.
Соединение GitHub CLI с api.github.com также требовало повторной проверки.

Перед продолжением проверить фактическое состояние, чтобы учесть действия,
выполненные при публикации этого файла.

```sh
git status --short --branch
git branch -avv
git remote -v
git log --oneline --all
gh api user --jq .login
```

Если ветка уже опубликована, продолжить её. Проверять наличие репозитория,
веток и PR перед созданием каждого объекта. Оценивать готовность по
содержимому и результатам проверок, а не по наличию названия ветки.

### Правила Git

- main используется для production, dev для интеграции.
- Прямые коммиты и push в main/dev запрещены, как и их удаление, force-push и rebase.
- Одна задача занимает одну рабочую ветку от актуального dev.
- Допустимые префиксы — feat, fix, refactor, test, docs, chore.
  Имена пишутся английским kebab-case.
- Коммиты оформляются естественным языком, простым списком.
  Автором остаётся пользователь. Co-Authored-By и атрибуция агенту запрещены.
- Перед push проходят тесты, линтер и сборка. Для неприменимой проверки
  требуется явное обоснование.
- PR рабочей ветки направляется в dev. Описание содержит изменения,
  способы проверки и риски.
- Мерж выполняется после явного подтверждения, merge-коммитом.
- После успешного мержа удаляется только соответствующая рабочая ветка,
  локально через `git branch -d`, затем на remote.
- PR dev → main создаётся исключительно по отдельной команде пользователя.
  После выпуска dev сохраняется.
- Переписывание истории и удаление другой ветки требуют отдельного согласия.

- [ ] Создать нативные манифесты и тонкие адаптеры для трёх агентов.

- [ ] Добавить каталоги установки из репозитория и инструкции установки,
  обновления и удаления для каждого агента.
- [ ] Добавить README, MIT LICENSE, AGENTS.md и примеры конфигурации/бэклога.
  CLAUDE.md и GEMINI.md должны ссылаться на общие правила.

| Агент | Основная команда |
| --- | --- |
| Codex | `$etask` |
| Claude Code | `/etask:etask` |
| Gemini CLI | `/etask` |

Аргументы команды принимают описание или ID задачи, `setup` либо
`review <ID>`. Пустой вызов выбирает следующую доступную задачу из
настроенной очереди. Если очередь отсутствует, агент запрашивает описание.
Выполнение начинается по вызову пользователя, установка лишь добавляет навык.

## 3. Настройка и данные проекта

- [ ] Режим setup исследует окружение и предлагает `.etask/config.json`.
  Запись выполняется после подтверждения. Повторный запуск сохраняет
  существующие настройки и посторонние инструкции.
- [ ] В конфигурации задать пути бэклога, очереди/команды, журнала решений
  и ручных проверок, команды тестов/линтера/сборки с рабочими каталогами,
  ревьюеров и необязательные настройки Jira.
- [ ] Локальная Markdown-задача содержит стабильный ID, тип, описание,
  критерии готовности, зависимости и исполнителя при командной работе.
  Свободное описание получает следующий свободный ID вида ET-<n>.
- [ ] ID связывает задачу, ветку и PR. При возобновлении использовать
  уже существующий PR задачи.
- [ ] Для Jira настраивать сайт, проект, поиск задачи и переходы статусов.
  Значения KAN, AH-<n>, участники и команды банковского проекта заменяются
  настройками целевого проекта.
- [ ] Авторизацию Jira получать через существующий Atlassian MCP.
  Конфигурация содержит параметры интеграции, секреты остаются в механизме авторизации.

## 4. Выполнение задачи

- [ ] Прочитать правила проекта, задачу, критерии готовности и связанные решения.

- [ ] Создать ветку от актуального dev либо продолжить существующий PR.

- [ ] Представить план с изменениями, тестами, контрактами, рисками

  назначить допустимого ревьюера. В Jira установить статус проверки и ссылку на PR.

## 5. Ревью, подтверждения и повторный запуск

- [ ] Режим review проверяет CI, локальные проверки, критерии задачи
  и ручные сценарии. Перед мержем показать результат и запросить подтверждение.
- [ ] Подтверждение push относится к показанному коммиту. Подтверждение
  мержа относится к репозиторию, номеру PR, base и head SHA.
  Изменившееся содержимое требует повторных проверок и соответствующего подтверждения.
- [ ] После разрешённого успешного мержа обновить dev, удалить только
  смерженную рабочую ветку и перевести Jira в завершённый статус.
- [ ] После частичного сбоя проверить реальные ветки, PR и состояние Jira,
  затем выполнить оставшиеся действия без дублирования объектов и комментариев.
- [ ] Ошибки обязательных инструментов и проверок сообщать конкретно.
  При выключенной Jira выполнять локальный процесс. Если Jira включена,
  а MCP недоступен, остановиться с диагностикой и инструкцией setup.
- [ ] Соблюдать режим планирования и более приоритетные инструкции проекта.
  Падение проверок в постороннем коде сообщать владельцу.
